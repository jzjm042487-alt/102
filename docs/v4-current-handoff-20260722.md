# V4 当前版本交接说明（历史快照）

> **状态更新（2026-07-24）**：本快照中的优先级、阶段和补丁建议不再生效。它仅记录当时问题；新工作必须遵循 `docs/SPEC.md` 与项目 Skill `production-grade-nesting-solver`。

> 目的：给下一位 agent/开发者一个可直接接手的完整状态说明。  
> 范围：当前 `V4 arc-flow + compress + CG fallback` 版本的真实表现、已做过程、有效思路、已解决问题、未解决问题、建议修复顺序。

## 1. 一句话结论

当前版本**不是“整体可交付”状态**，但已经明确分成了两部分：

1. 在一批精选样本和部分真实语料上，V4 已经能明显优于老软件，尤其在焊口数上。
2. 在真实中等难度语料上，仍存在三类硬问题：
   - 简单 2 管型案例仍会 `无解/超时`
   - 部分案例焊口数劣于老软件
   - 部分案例虽然焊口不差，但拼法/切法种类明显更散

因此，下一步不能再泛泛调参，必须按优先级逐项修：

1. **先修“无解/超时”**
2. 再修“焊口劣”
3. 最后修“拼法/切法散乱”

## 2. 当前版本做了什么

本轮已经把 V4 从“只有 arc-flow 主解”推进到“主解 + 压缩 + 部分 CG 兜底”的组合版本，核心变化如下。

### 2.1 已接入/保留的核心能力

- `scripts/_arcflow_v3.py`
  - 增加 `CG fallback` 接口 `_try_colgen_fallback()`
  - 增加残料对齐段 `_residual_seg_lengths()`
  - 增加 residual grid 门控，只在“少管型 + 存在超长管”时启用
  - 保留 `_better_of()` 作为纯切/焊接解选择器
  - 保留 `_util_floor()`，验收口径是 `max(0.95, legacy_util - 1e-3)`

- `scripts/_exp_colgen.py`
  - 增加 `solve_colgen_full()`
  - 增加 FFD 种子 `ffd_weld_seed()`
  - 增加超长管残料分解候选 `_residual_split_lengths()`
  - `solve_integer()` 改成更接近 SPEC 的词典序求解：
    - 先定 material 上界
    - 再优先压焊口
    - 再尽量压拼法/切法

- `backend/app/route_c_bp.py`
  - 在 branch-and-price 后接入 `_compress()`，把 arc-flow 里的 `_compress_types()` 复用过来
  - 给压缩过程留出专门时间预算，避免 LP/ILP 把预算全部吃光

### 2.2 已修正的数据基线

- `scripts/_picked20_full.json`
  - 已确认并修正 8 个伪基准：
    - `L2/L5/L7/L9/L10/L11/L18/L19`
  - 这些档老软件在原始语料里其实没有成功输出
  - 当前处理方式：
    - `legacy = null`
    - 原来的伪数字保留在 `legacy_claimed`
    - `legacy_status = "no_result"`

这一步非常关键，因为之前大量“追不上老软件”的分析，其实是在追假的 baseline。

## 3. 这轮过程中确认过的关键事实

### 3.1 词典序口径

用户已经拍板，按 `SPEC.md`：

1. 焊口数
2. 拼法种类
3. 切法种类
4. 段种类
5. 利用率

其中利用率不是第一目标，而是**硬底线约束**。

### 3.2 利用率硬底线

验收口径必须使用：

```text
util_floor = max(0.95, legacy_util - 1e-3)
```

如果没有 legacy，则至少用 `0.95`。

### 3.3 一个已确认的脚本级坑

我在中途写 `_cmp_metrics.py` 时，最初没有把 `legacy util_floor` 传给 `solve_arcflow()`，导致 L4 出现了错误判断：

- 老软件：`0 焊口 / pure_cut / util 0.9661`
- V4 错误地选了：`23 焊口 / 高 util 焊接解`

原因不是求解器本身，而是脚本用了错误 floor，退回到 `group.target_rate`，把老软件纯切解误判成“不达标”。

后来已修正：

- `_cmp_metrics.py` 调用 `solve_arcflow(..., util_floor=legacy_util)`

这说明：**所有后续验收脚本都必须显式传 legacy floor**，否则结论不可信。

## 6. 这轮过程中验证过的“有效思路”

下面这些方向不是空想，是已经在样本上验证过有效的。

### 6.1 “util 只做 floor，不做主目标”

这是必须坚持的。

如果 util 参与主导排序，会把很多“0 焊口纯切解”挤掉，导致词典序失真。

### 6.2 compress 阶段确实能明显压拼法/切法

在多档案例里，最终 solver 落在：

- `compress`
- `pure_cut`

说明 `compress` 不是摆设，它对 L8/L12/L13/L16/L17 这些档确实有贡献。

### 6.3 少管型 + 需多段焊接时，残料对齐段是有效的

L11/L9/L20 一类问题说明：

- 固定 step 网格不够
- 必须把 `L - k*S`、`S - k*L` 这类残料对齐段纳入字母表

这不是可选优化，而是建模能力的一部分。

### 6.4 真实语料里存在“纯切直接碾压老软件”的档

例如：

- idx `2596`: V4 `0 焊口` vs 老软件 `18 焊口`
- idx `598`: V4 `0 焊口` vs 老软件 `7 焊口`

这说明老软件不是全局最优，V4 的建模方向不是错的。

## 7. 这轮过程中暴露的“无效/不够用的思路”

### 7.1 单纯加大总时限无效

之前对 L9/L11 的 600s 重跑已经证明：

- L9：仍退 `ffd_weld`
- L11：仍卡在 213 焊口附近

根因不是“搜得不够久”，而是**离散段集缺关键段**。

### 7.2 只靠 arc-flow 主流程无法解决 L20

L20 的真实问题不是利用率，而是：

- 拼法过散
- 切法过散
- 焊口仍高

当前 `CG fallback` 加了规模闸门后，不会再挂死 13 分钟，但也因此无法真正处理 L20。

### 7.3 当前 type compress 对“简单 2 管型档”并不稳

真实语料里最刺眼的问题不是 L20，而是一些简单的 2 管型档：

- 直接无解
- 或焊口劣
- 或虽然焊口优一点，但拼法/切法完全炸开

这说明当前压缩器不是“稳态生产级”。

## 8. 已解决的问题

下面这些问题已经明确解决，可以视为本轮成果。

### 8.1 修正了 picked20 里的假基准

这一步解决了“追错目标”的根问题。

### 8.2 修了大规模档 CG fallback 挂死问题

之前 L20 会在 CG fallback 上挂死十几分钟。现在：

- 超大需求档直接跳过 CG fallback
- 至少不会把整个求解卡死

### 8.3 修了验收脚本 floor 使用错误

`_cmp_metrics.py` 已改成按 legacy util 传 floor。

### 8.4 明确了真实验收口径

后续任何 agent 都不应该再争论目标函数顺序和 util 底线。

## 10. 建议下一位 agent 的修复顺序

这是最关键的一节。

### 阶段 A：先修“简单档无解”

推荐顺序：

1. 先拿 `idx 2318`
   - 因为它 68s 就返回无解
   - 复现成本最低
2. 再看 `idx 2345`
   - 85s 返回无解
3. 再看 `2149/1613/1239/1467/2450`
   - 这些是被 200s 硬超时杀掉的

建议做法：

1. 单档 verbose 诊断
2. 先判断：
   - 是 `classify_group()` 错判
   - 还是 arc-flow 建模 infeasible
   - 还是 `compress`/`cg fallback` 没接住
3. 如果是 2 管型简单档，优先怀疑：
   - util floor 过紧
   - 段集缺关键残料段
   - pure_cut 与 weld 解比较逻辑有误
   - 某类 weld point 未被纳入

### 阶段 B：再修“焊口劣”

推荐先看：

1. idx `1503`（45 vs 19，差距大）
2. idx `1297`
3. idx `1107`
4. idx `1365`

这类档要分析：

- 老软件是否用了某种稳定的 2 段/3 段模式
- 当前 `residual grid` 是否没覆盖到
- `compress` 是否在“固定焊口 cap”下仍枚举不出老软件那种少拼法方案

### 阶段 C：最后修“花样散乱”

重点案例：

1. idx `2612`
2. idx `2201`
3. L16
4. L20

其中：

- `2612` 是中等难度真实语料里的代表
- `2201` 是“焊口赢了但花样炸裂”的典型
- `L16` 是精选样本里的代表
- `L20` 是最大规模终极档

## 13. 当前版本的最终判断

当前版本可以这样评价：

- **不是失败版**
  - 因为它已经在多档上实打实超过老软件
- **也绝不是可收尾版**
  - 因为真实语料上仍有大量简单档无解/焊口劣

更准确地说，它是一个：

> **已经验证方向可行，但远未达到稳定工程化验收标准的中间版本。**

下一步应该停止泛泛“大样本跑分”，而是围绕：

1. `idx 2318` 一类简单无解档
2. `idx 1503` 一类焊口劣档
3. `idx 2612 / 2201` 一类花样散乱档

逐个击破。
